# Issue #147 — Optimized Mix missing-category recommendations

## Status

This report addresses Issue #147 as a **documentation and decision-boundary slice**. It does not change runtime behavior or visitor-visible wording.

## Finding

The missing-category panel is rendered by `v3-webapp/client/src/pages/Home.tsx` from the calculator result. The category recommendations are generated by `MultibirMixCalculator.detectMissingCategories()` in `v3-webapp/client/src/lib/calculator-multi-bird.ts`.

The current implementation uses fixed recommendation arrays:

| Category | Current recommendation values |
|---|---|
| Grain | `wheat`, `barley`, `oats` |
| Legume | `peas`, `lentils`, `mung beans` |
| Oil seeds | `safflower`, `sunflower`, `flaxseed` |

These values are examples supplied by `CATEGORY_RECOMMENDATIONS`; they are not calculated from the visitor's inventory and are not an exhaustive catalog. The current panel renders each value as a separate badge. The calculator does not currently label the values as examples.

The missing-category reason strings are also fixed category explanations:

| Category | Current visible reason |
|---|---|
| Grain | `No eligible grains are available — grains are essential for energy and carbohydrates.` |
| Legume | `No eligible legumes are available — legumes are essential for protein and amino acids.` |
| Oil seeds | `No eligible oil seeds are available — oil seeds contribute fat and ingredient diversity.` |

## Reproduction and source reconciliation

The active runtime source confirms that the recommendations are fixed constants and that missing categories are detected from the categories of eligible inventory entries. The active Home page confirms that `missingIngredients` is rendered directly as the red `Missing Essential Ingredients` panel with the category, reason, and recommendation badges.

The existing optimizer bridge test confirms that missing-category data is passed through unchanged between the synchronous calculator result and the optimizer result bridge. No separate test currently asserts the exact recommendation copy or the example-list semantics.

## Proposed owner decision

The likely visitor-facing correction is to make the example status explicit in the panel, for example by adding `e.g.` before the recommendation badges or by using an equivalent owner-approved phrase. **No wording is proposed for implementation by this PR.** Public-facing copy requires the product owner's explicit approval before any code change.

If approved later, the follow-up implementation must enumerate every visible string changed, quote the exact before and after wording, add a focused regression test, and preserve the existing red warning styling and dynamic missing-category detection.

## What this PR does not change

This PR does not change active ingredient data, nutrient values, formulas, calculator behavior, inventory semantics, safety rules, warning severity or color, visitor-visible copy, Firebase configuration, Firestore region, deployment, or the primary mix panel.
